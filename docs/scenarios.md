# 練習シナリオの答え合わせ

すべて架空のログです。以下は作成者が定めた想定正解であり、AIが生成した回答や実障害の実績ではありません。この文章はAPIに送信しません。
ログを編集すると行番号や想定正解も変わるため、同梱の未編集ログで照合してください。

## 1. 接続タイムアウト：接続先ポートの設定誤り

- 1行目：gatewayの接続先ポートが8081へ変更された
- 2〜4行目：8081への接続拒否、再試行後の時間切れ、503が同じ要求で発生
- 5〜6行目：接続先プロセスは稼働、待受けは8080。接続設定との不一致がある
- 7〜8行目：8080への修正後、同じ要求の再試行が200で成功
- 9行目：その後の観測ではエラー0件

期待する説明：設定変更により接続先ポートが不一致になったことが、障害の直接原因として強く支持される。
タイムアウトだけを見て「ネットワーク障害」と終える回答より、具体的な設定差分と復旧を関連付けた回答を評価する。
設定を誰がなぜ誤ったか、以後も再発しないかは分からない。

## 2. ディスク逼迫：保存先の容量不足

- 1・3行目：同じ請求書出力ジョブがdemo-dataへの書込みでENOSPCにより失敗
- 2・4行目：容量使用率が98%から100%へ増加。inode使用率は12%
- 5行目：DB・通信のヘルスチェックは正常
- 6〜7行目：容量拡張後、同じジョブの再試行が成功
- 8行目：その後の観測では出力エラー0件

期待する説明：出力先の空き容量不足が直接原因として強く支持される。
inode不足より容量不足を優先する。容量が増えた理由や不要ファイルの所在までは断定しない。

## 3. 認証失敗：資格情報の有効期限切れ

- 1〜3行目：同じバッチが資格情報demo-key-oldを使い、401とcredential_expiredで失敗
- 4行目：失敗より前の11:59に期限切れになっている
- 5行目：権限変更は記録されず、通信確認は正常
- 6〜8行目：有効な資格情報への切替後、認証確認と同じバッチの再試行が成功
- 9行目：その後の観測では認証失敗0件

期待する説明：資格情報の期限切れが直接原因として強く支持される。
権限不足・パスワードの入力ミス・不正アクセスを根拠なく断定しない。
credential_refは架空の管理名で、実際の秘密鍵はログに含めていない。

## 4. 通常ログ：観測範囲内で障害の兆候なし

- 2行目：HTTP 200、応答時間24ms
- 3行目：DBの確認は正常、接続数12／上限100
- 4行目：容量45%、inode8%
- 5〜7行目：待ちジョブ0、失敗0、認証確認成功、帳票作成成功
- 8行目：60秒の観測でエラー0件

期待する説明：提示された範囲で障害を示す記録はない。findingsは空でもよい。
「将来も正常」「全サービスに問題なし」とは言えない。通常時にも架空の原因や重大アラートを出さないかを見る。

## 手動評価の記録方法

各サンプルをLLMモードで1回ずつ実行し、次を記録する。未実行の欄は未実行のままにする。

| 項目 | 記録する内容 |
|---|---|
| 実行日時・モデル | 接続記録に表示される値 |
| 応答ID | APIから返されたID。秘密鍵は記録しない |
| 原因候補 | 想定正解と合うか。単に障害の種類だけを挙げていないか |
| 根拠行 | 存在し、その説明を支えているか |
| 復旧との関係 | 同じ処理の再試行成功まで関連付けているか（障害3種） |
| 過剰な推測 | ログにない事情を事実として追加していないか |
| 改善点 | 不十分だった説明・不足するログ |

正解に合う1回の回答だけで、未知の実務ログでも正確だとは評価しない。
生成されたレポートと実画面を残し、応募時は「架空ログの検証シナリオで確認」と説明する。
